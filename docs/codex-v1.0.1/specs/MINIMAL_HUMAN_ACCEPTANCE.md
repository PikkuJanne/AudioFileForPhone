# One consolidated owner session — prepare, do not improvise

## Owner-facing instructions (maximum one short page)

Codex produces an Acceptance-Kit ZIP at S13/S14, not a list of PowerShell commands.
It contains the exact frozen runtime package plus a tested runner, short synthetic
fixtures where appropriate, an instruction sheet, and report/export controls. Do
not redistribute FFmpeg binaries without a reviewed distribution decision; the kit
uses the normal setup selection or the optional pinned vendor download with consent.
No Git, Python, Pester, SDK, FFmpeg command typing or admin elevation is required.

The intended owner actions are:

1. Extract and double-click Run-Windows-Acceptance.bat. Choose the existing source
   audio folder through the picker. If needed, use the normal setup UI to select
   the existing FFmpeg bin directory once. No PATH editing or version commands.
2. Follow the kit's single real shortcut/drop instruction and press Enter to use
   defaults. The kit prepares and opens the appropriate shortcut/source locations.
   It performs and collects mechanical checks; no manual counts or log hunting.
3. Open the selected output on the phone, play a short section and seek near the end.
   Answer the kit's simple observed yes/no/not-tested questions and return the one
   generated support report. No full audiobook listening or phone matrix.

This is an intended minimal path, not a false guarantee that a failing machine
needs no further action. Any retest is limited to the affected path after a fix.
The owner has already supplied environment/discovery data: never ask for it again.
Do not ask to upload audio or full logs. No hidden publication of reports.

## What the kit automates

First verify the exact candidate ZIP and runtime file hashes. Detect real OS/build,
PS5.1/PS7 availability, config/dependency state and selected tools automatically.
Use the shared production diagnostics/resolver. Run unattended tests in isolated
owned output/config scopes, with a child PATH that reproduces unavailable discovery.
Test persistence in a separate fresh process. Do not assert first-run success from
a test which secretly repaired PATH or copied tools beside the application.

Before the real collection, automatically copy one selected supported file into
an owned one-file input and verify its conversion in the required available hosts
without modifying the source. Retain a local source hash manifest; do not export
private paths or content hashes unless needed and consented. The real batch then
uses the actual packaged BAT/desktop shortcut with the original selected folder,
not a developer checkout or a special bypass launcher. Both the one-file and full
batch must produce valid results. Capture source hashes, output counts, actual
media format/duration/bitrate, manifests and final result. No mere file existence.

For the real desktop route, production Music default output may be used. Reserve/
identify that exact new run; do not clean or scan unrelated Music collections.
Keep its completed files for the owner. Automated CLI cases use OutputParent in an
owned temporary tree. Do not spoof the registry Music folder or suppress traversal/
validation for tests. Track correlation by actual run ID/source/package identity,
not just a timestamp-name guess or 'newest directory'.

Capture raw BAT exit in controlled launches; for physical Explorer observations,
record how outcome was obtained. A manifest result is not a captured raw process
exit. If an actual physical folder drop cannot be controlled automatically, request
that single owner gesture and one simple completion confirmation, then inspect the
exact resulting manifest/output mechanically. Do not turn a simulated shortcut
launch into an asserted observed physical drag-and-drop.

Long duration: automatically generate and fully decode a long synthetic fixture
or test an existing long source where available. The basic phone check uses a
candidate-generated output from this kit. Only that phone/player observation is
claimed. Existing old-release phone acceptance is not a new-candidate pass.

## Windows 11 and missing platforms

Codex should complete Windows 11 host, picker and package checks on its own Windows
machine/VM and keep them out of the owner's session. On this known Windows 10
machine, PS5.1 and Store PS7 are expected from the prior report, but record fresh
observations. When another real client environment is genuinely unavailable, the
same kit is the fallback. Mark release acceptance BLOCKED until required evidence
exists; do not delegate dozens of manual checks or pretend Server covers it.

## Report content and decisions

One REPORT.txt for the owner, plus a local machine-readable JSON companion if useful.
The export includes package/runtime IDs; OS/host versions; dependency origin/build;
case IDs, status and exit; counts; duration/bitrate validation; source-unchanged
boolean; and exact human observations. Redacted excerpts only, not all private data.
Never prefill human answers as pass. Include NOT_TESTED/FAILED alternatives.

Normal completion requires the valid collection fully converted, zero per-file
failures, no unprocessed supported files, unchanged sources, valid media and exit 0
for controlled runs. Corrupt-fixture partial failures are separate expected-negative
cases, never mixed into the normal owner's valid-batch gate. On failure show one
specific issue and preserve evidence. Do not ask the owner to diagnose it.

## Repeat policy

The candidate hash tested is binding. A documentation-only repository checkpoint
outside the package does not require another owner run. Changed packaged bytes
require automatic exact-package checks. Changed setup/launcher/encoding/cancellation
or shared dependencies require the affected client/owner path to be rerun; keep
human work to the simplest meaningful check. Do not waive a runtime-change retest
just to keep the manual test count low.
